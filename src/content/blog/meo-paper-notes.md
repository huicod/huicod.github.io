## 一句话总结

MEO 把“把这段右腿侧踢再踢高一点，之后双手护脸”这样的修改，先翻译成**操作哪个关节、在源动作的哪个时刻、朝什么方向改**的程序，再生成关键姿态并补全附近的过渡运动；编辑后的动作存入历史，下一轮可以继续修改或回退。它的核心是将语言意图、可执行编辑和连续动作生成分工处理。[§2、§4，图1–2][paper]

## 研究背景与动机

**领域现状：** 动画师经常从已有动作开始工作，再逐步调整细节。传统关键帧编辑能明确操作关节，却需要手工选择帧和调节参数；文本到动作模型降低了生成门槛，但修改提示词后重新生成，通常不能保留原动作的逐帧结构。[§1、§3][paper]

**现有痛点：** 输入“侧踢”再换成“更高的侧踢”，系统可能换了朝向、节奏、手臂姿态甚至整个动作。另一方面，“踢完以后护住脸”不仅包含手部目标，还要求理解哪个动作是踢腿、何时算踢完、修改应持续到哪里。把整句话直接交给生成器，很难定位是哪一环出了问题。[图1、§2][paper]

**核心矛盾：** 用户表达的是相对于当前动作的修改意图，而生成器通常学习从条件到完整动作的分布。好的编辑既要执行新要求，又要尽量保留无关部分，还要有自然过渡；这三者有时冲突，例如踢得更高需要躯干配合和更长准备时间。[§2][paper]

**本文目标：** 支持对已有角色动画进行细粒度、可预测、可多轮修正的语言编辑。作者围绕三个目标评价结果：遵从编辑意图、保留原动作结构、保持动作合理性，并允许用户继续细化或纠正上一轮要求。[§2、§5][paper]

**切入角度：** 在语言和关节数值之间加入一层语义明确的编辑算子。算子能查询源动作中的极值时刻，表达关节旋转、平移、相对位置和变速；这样语言模型负责选操作与参数，实际坐标由执行引擎结合源动作计算。[§4.1–4.3][paper]

**核心 idea：** 让预训练语言模型在 API 文档与程序示例的提示下生成 MEO 程序，执行后得到稀疏关键帧或时间变换，再用学习到的动作先验补齐局部过渡。程序、关键帧、补全结果各有明确职责，且每次结果都能作为下一轮编辑的输入。[图2–5][paper]

## 方法详解

### 整体框架

输入包含三项：源动作 X<sub>S</sub>、源动作的文字描述 E<sub>ctx</sub>、本轮编辑指令 E；多轮时还加入之前的指令、程序和动作版本。语言模型生成 Python 形式的 MEO 程序。执行器选出源动作中的具体帧，计算目标姿态；上下文帧和目标姿态构成条件 C，轨迹回归与身体扩散补全生成连续动作 X<sub>E</sub>。变速算子通过时间扭曲执行，可直接作用于源动作或空间编辑后的结果。[§2、§4][paper]

读图时先看“语言→程序”，再沿源动作支线看程序如何落到具体帧和关节，最后看补全与版本缓存。**语言模型没有直接读入完整3D动作张量：它依靠文字上下文选择操作，运行时查询函数才读取真实关节轨迹。** 编辑程序的格式通过检查，也不意味着最后生成的动作已经满足所有空间或物理要求。[§4.2–4.3][paper]

### 关键设计

1. **MEO 是相对于源动作的编辑指令，而非整段动作描述。**

   一个典型算子包含目标关节、修改方向和作用时刻。旋转可表示屈曲/伸展、外展/内收；平移可表示向上、向下、向前等；相对位置可表示手在头部前方或肩膀上方。时间可以是具体帧，也可以是“腰部最高时”这样的查询。[§4.1][paper]

   | 编辑成分 | 示例含义 | 数值从哪里来 |
   | --- | --- | --- |
   | 关节与方向 | 右髋外展、右脚上移 | 语言模型从支持的 API 参数中选择 |
   | 相对空间关系 | 右手移到头部前方 | 执行器读取当前关节位置与姿态，构造目标 |
   | 时刻与区间 | 第0帧、脚最高时、动作中段 | 显式索引或实际源动作轨迹查询 |
   | 动作起始语义 | 从这里开始抬膝 | 将起始时刻与未来目标姿态区分 |
   | 速度 | 加快、放慢、停顿 | 时间扭曲器重映射动作的采样时刻 |

   作者刻意让语言接口主要选择离散方向，不要求 LLM 输出“增加10.2厘米”这类精确数字。旋转幅度依据当前关节角与设定范围按程序计算，平移幅度也由执行规则给出。因此可解释性来自“选了哪个操作、相对什么改”，并非每个自然语言形容词已经具有唯一数值定义。[§4.1、§4.3.2][paper]

   当前发布代码分别实现 `do_rotate`、`do_translate`、`do_relative_translate`、`do_change_speed` 和 `do_fix_joint` 等入口；支持范围由参数检查与执行器共同限定，不能由“原则上可处理SMPL关节”推成所有关节和方向都已实现。[算子实现][interpreter]、[参数检查][assertions]

2. **用已有语言模型合成程序，靠运行错误修正接口调用。**

   提示中给出 API 名称、允许的关节/方向列表和少量指令—程序示例，再放入 E<sub>ctx</sub> 与 E，让 ChatGPT-4 补完程序。程序注释说明选择哪些关节、何时修改、应加载哪个动作版本；没有为这项任务微调语言模型。[§4.2、图3][paper]

   程序若调用未支持函数或非法参数，系统把错误反馈给语言模型，重新生成。官方代码在 `response_to_code` 中检查调用，重试计数达到3时退出。这一环节处理的是接口与参数错误；例如“误把左脚当右脚”可能仍产生合法程序，最终脚部目标也可能经过补全后偏离。[语言前端][frontend]、[参数检查][assertions]

   多轮对话保存先前指令和程序，并提供 `load_motion` / `save_motion`。若用户说“再高一些”，通常从最新版本继续；若说“不，是另一只手”，则可能退回修改前的版本，再执行正确操作。这里的 undo stack 存储动作版本，不是一个持续求解所有历史约束的全局优化器。[§4.2.3–4.2.4][paper]

3. **把时间词落到源动作：查询极值，不把语言推理当成动作检测。**

   显式帧号可以直接执行；隐式时间描述由运动学启发式求解，例如对指定关节的高度曲线取极大值。算子还区分“这个时刻已经处于某姿态”和“从这个时刻开始做子动作”：后者需要寻找之后的目标帧。[§4.1、§4.3.1][paper]

   官方 `frame_picker.py` 的 `when_joint` 对高度求 argmax/argmin，`furthest_from_body` 查询相对根位置的水平距离；涉及动作起始的路径会向后寻找关节变化极值。这让程序能依据真实动作执行，但并没有训练一个能普遍识别“踢腿结束”“完成抓取”等语义事件的识别器。[选帧实现][frames]

4. **先求目标关键姿态，再让生成模型处理过渡。**

   选定帧后，旋转操作改变局部关节姿态并用前向运动学传播；平移操作通过逆运动学等机制寻找能到达目标位置的姿态。原文把幅度设定为程序规则，例如把关节朝限位移动一部分。变速使用基于样条的时间扭曲，以指定区间端点约束时间映射。[§4.3.2][paper]

   当前实现中，脚部平移走解析腿部 IK；普通手部平移另有结合无条件动作先验的求解路径。两者不能一概写成“LLM直接给出关节角”。空间操作得到的是待整合的关键姿态，关键姿态本身也不自动具备平衡、碰撞避让或自然的进出速度。[空间执行器][keyframer]、[平移实现][translation]

5. **以源上下文与关键帧为条件，学习局部过渡补全。**

   在目标关键帧 k 的前后留下宽度 W 的待补全窗口，将这些位置置零；窗口外保留源动作，关键帧位置放入编辑后的姿态。训练时从真实 AMASS 动作随机选关键帧和窗口，以原动作作为重建目标。推理时才将关键帧换成实际编辑结果。[§4.3.3、图4][paper]

   <div class="equation">C = 已保留的源动作上下文 + 编辑后的关键姿态<br/>M = 1：已知属性；M = 0：需要补全的属性<br/>inputₜ = M⊙C + (1−M)⊙Xₜ，cond = C<br/>L = E ‖X − G(inputₜ, C, t)‖²</div>

   这里是根据原式2–3整理的等价流程记法，C 已在未知处置零。去噪器 G 预测干净动作 X，而非仅预测噪声。主输入包含已知值和未知区的噪声，另一条件支线单独输入 C；两路经嵌入融合，加入扩散步与位置编码，送入 Transformer-decoder。[图5、式2–3][paper]

   **根轨迹与身体分两步。** 作者发现跳跃、下蹲等根部编辑更适合先补根轨迹，因此先训练回归模型预测根轨迹，再把它加入 C，由扩散模型补齐其余身体运动。当前 `TrajectoryWrapper` 是一次前向回归调用，并不是另一套迭代扩散采样。[§4.3.6][paper]、[轨迹实现][trajectory]

   **插值只作为引导。** 对非根部编辑，先把目标关键姿态以简单插值融入源动作，得到 X<sub>spline</sub>。采样早期混入适当加噪后的插值结果，随去噪推进逐渐减弱其权重，让生成先验补充细节；完整方法不是把关键帧直接样条连接后就结束。[§4.3.5、图5][paper]

   **旧信息也进入条件。** 显著极值帧和此前编辑过的帧被额外保留，降低局部遮罩把关键结构一并抹掉的风险。不过原文明确说 C 中的关键帧与源上下文不应视为严格时空硬约束；更大的姿态位移还可能需要更长过渡时间。[§4.3.6、§6][paper]

### 一个完整例子

沿用论文图1的右腿侧踢，下面的中间表示是教学展开，最终示例见作者演示。[图1][paper]

1. **给出源动作与上下文。** X<sub>S</sub> 是现有侧踢动画，E<sub>ctx</sub> 说明“用右腿侧踢”，用户提出“踢得更高”。语言模型依靠这条上下文选择右侧关节，而非从骨架张量中直接识别踢腿。
2. **生成编辑程序。** 程序加载当前动作，选择脚部上移或髋部旋转等受支持操作，并用右脚高度等查询确定对应时刻。此处具体采用哪组算子由生成的程序决定；不能把教学示例当成每次必然输出的固定代码。
3. **执行关键姿态修改。** 选帧器在源轨迹上得到实际索引，运动学模块把该帧变成更高的踢腿姿态。保留其他关键帧，在目标前后开过渡窗口。
4. **补齐局部运动。** 根轨迹回归先提供相容的轨迹条件，身体扩散结合源上下文、目标姿态与可选插值引导，生成连续过渡，再保存为新版本。
5. **继续说“踢快一点”。** 系统结合上一轮对话定位踢腿区间，对当前版本施加时间扭曲。这轮主要修改运动时间安排，不需要把“快”当成新的全身姿态条件重新生成整段动作。
6. **再说“踢完后双手护脸”。** 生成手部相对头部位置的算子，选择踢腿之后的时段，执行新的关键姿态与补全。若结果未达到用户意图，可继续澄清或回退版本；系统没有因程序成功执行就自动宣布所有要求已通过物理验收。

## 实验关键数据

### 主实验

**用户研究，原表1。** 19位参与者分别评价9组 MDM-Edit 对照和9组 MoMask-Edit 对照，三项均为1–5分。两组实验使用不同来源的源动作，不能把两个 Ours 行合并成一组统一样本。[§5.3.1–5.3.2，PDF第6–7页][paper]

| 源动作与比较方法 | StrucSim ↑ 原结构保留 | Fidelity ↑ 编辑意图符合 | Qual ↑ 动作质量 |
| --- | ---: | ---: | ---: |
| MDM · MDM-Edit | 2.77 | 1.56 | 3.79 |
| MDM · 本文 | **4.33** | **4.48** | **4.07** |
| MoMask · MoMask-Edit | 3.59 | 1.72 | **3.88** |
| MoMask · 本文 | **4.25** | **4.52** | 3.77 |

MDM-Edit 固定随机种子，把原描述与编辑指令拼接后重新生成；MoMask-Edit 可做掩码编辑，但不能自行确定掩码帧，作者为它提供了本方法语言解析器确定的时间中心。因而对照不只是“有没有LLM”，还比较了不同的执行机制。[§5.3.1][paper]

**自动评估，原表2。** 对每个基线另外评测17对编辑动作。Fidelity-Auto 是作者根据关节位置编写的二值编辑测试通过比例；G-MPJPE 衡量编辑动作与源动作的几何差异，越低表示改动越少。它不是对一条唯一正确编辑动画的重建误差。[§5.3.3，PDF第7–8页][paper]

| 指标 | MDM-Edit | 本文：MDM源动作 | MoMask-Edit | 本文：MoMask源动作 |
| --- | ---: | ---: | ---: | ---: |
| Fidelity-Auto ↑ | 0.588 | **0.82** | 0.6 | **0.882** |
| G-MPJPE ↓ | 0.247 | **0.08** | 0.181 | **0.063** |

保留原表数值尺度；该表未标注物理单位。原表注报告 Wilcoxon 配对检验：与MDM对比，Fidelity p&lt;0.03、G-MPJPE p&lt;0.0003；与MoMask对比，分别为 p&lt;0.02、p&lt;0.0002。原文“0.88对0.6，140% higher”的文字与数字不符；按原表0.882和0.600计算是提高0.282、相对约47%，本文不沿用该百分比。[原表2与§5.3.3][paper]

**程序可执行性，作者项目页的额外说明。** 对100条由人工及ChatGPT辅助构造的编辑提示，首次生成90条可执行程序，反馈重生成又解决7条，3条失败。此处统计的是程序可执行性，不是97%的完整动作编辑成功率。[项目页FAQ][project]

| 程序生成结果 | 提示数量 |
| --- | ---: |
| 首次生成即可执行 | 90 |
| 经反馈重生成后可执行 | 7 |
| 仍未执行成功 | 3 |

### 消融实验

**两阶段补全与样条插值：** 使用100段真实 AMASS 动作，每段配1–3个MEO。完整执行器 ENG 先补根轨迹再补身体；ENG-SS 改为单阶段全身补全；ENG-Interp 用样条代替身体扩散补全。下面将 §5.3.4 原文报告整理成表，并非新增实验。[PDF第7–8页][paper]

| 设置 | FID<sub>g</sub> ↓ |
| --- | ---: |
| AMASS-Source：原始动作 | 4.33 |
| ENG：完整两阶段执行器 | **4.95** |
| ENG-SS：单阶段全身补全 | 5.25 |
| ENG-Interp：样条插值替代扩散 | 8.05 |

FID<sub>g</sub> 在 fairmotion 几何特征空间计算，参考分布为1000段真实动作。编辑应尽量保留源动作，故作者希望它接近源动作的4.33，而不是宣称编辑后的分布必须比源动作更接近参考分布。该消融支持两阶段补全和学习到的过渡先验；没有单独给出移除会话历史、极值帧保留或插值引导的量化消融。[§5.3.3–5.3.4][paper]

### 关键发现

1. **优势集中在遵从编辑与保留源结构的同时改善。** 两组人评的 Fidelity 都达到约4.5分，StrucSim 也超过4.2分。自动指标进一步支持“既改到目标、又减少无关改动”，但G-MPJPE单独低并不充分：完全不编辑也可能很低。[表1–2][paper]
2. **动作质量没有全面领先。** 对MoMask源动作，本文Qual为3.77，低于MoMask-Edit的3.88；作者也未在主对比上给出跨方法FID<sub>g</sub>排名，因为源动作本身由不同生成模型产生。编辑接口更明确和动作整体质量更好是两个问题。[§5.3.2–5.3.3][paper]
3. **执行器对自然过渡很重要。** 单纯插值的FID<sub>g</sub>为8.05，完整方法为4.95；根轨迹与身体分开还比单阶段的5.25略好。它说明关键姿态之外仍需要运动先验，不等于所有目标关键帧都能被自然、精确地实现。[§5.3.4][paper]
4. **证据规模与目标需要同时看。** 19人研究、每基线17对自动测试及100段执行器消融，覆盖了所展示的运动学编辑场景；没有由此证明长期多轮约束、环境碰撞或任意语言要求的可靠执行。程序通过检查、二值编辑测试通过、整段物理合理性应分别评估。[§5–6][paper]

## 亮点与洞察

- **把相对修改变成明确接口：** “更高”“另一只手”“之后”依赖当前动作和对话。MEO把这些词分别映射到空间操作、关节选择和时间查询，使每次修改有可追踪的中间对象。[§4.1–4.2][paper]
- **语言模型与动作数据在运行时对接：** LLM不必直接掌握完整骨架张量，通过查询源动作的程序把文字计划落到具体时刻。这是利用语言能力的可实现方式，但也暴露了极值启发式的适用范围。[§4.3.1][paper]
- **把会话中的纠正落实到版本选择：** undo stack不只是保存聊天文字，还决定后续操作施加在哪个动作版本上；“继续改”和“撤回重做”因而可以产生不同执行路径。[§4.2.4][paper]
- **编辑表示与生成先验可以分别扩展：** 增加新算子时，要补齐API示例和执行逻辑；已有补全器可以继续负责局部过渡。这个模块化设计比把所有新要求都当成重新训练文本生成器更易定位问题。[§4][paper]、[项目页讨论][project]

<span id="reading-6" class="reading-anchor"></span>

## 局限与展望

- **运动学编辑范围明确。** 系统支持关节姿态、位置、时间等修改，不能直接处理“更用力地跳”“更兴奋地完成”这类动力学或风格要求。新增一个语言词并不够，还需要定义可执行算子及其运动效果。[§6][paper]、[项目页FAQ][project]
- **时间定位受启发式限制。** 目前主要依据关节极值；重复动作、多次极值和复杂事件语义可能导致选错时刻。后续可以改进事件识别，但仍需把“语言引用了哪个事件”与“执行在哪个帧”单独验证。[§6][paper]
- **稀疏目标不是最终硬保证。** 原文明确承认源上下文与编辑关键帧只是条件。若位移较大但过渡窗口不够，可能发生速度不一致；多轮修改也可能影响旧要求。精确接触、碰撞、平衡与未编辑部位保持，需要针对最终动作另外测量。[§6][paper]
- **程序合法性检查覆盖有限。** 代码中的检查主要限制算子、关节和方向，不能证明语义选择正确。作者项目页指出生成可执行程序已相对容易，更难的是程序是否真正表达了用户意图。[项目页FAQ][project]、[检查实现][assertions]
- **公开原型仍需适配。** 官方README说明它是研究原型，完整路径依赖外部动作数据、SMPL模型、模型权重和语言模型服务，输入表示也不同于常见HumanML3D数据。资源入口存在不等于已验证本机能直接复现或满足实时交互延迟。[官方README][repo]

## 相关工作与启发

- **[ProgPrompt](https://arxiv.org/abs/2209.11302)：** 以API和示例提示语言模型生成可执行计划，是本文程序提示设计的重要参照。MEO把该思路落到关节、源动作时刻和动画版本，而非直接控制通用机器人任务。[§3、§4.2][paper]
- **[MDM](https://guytevet.github.io/mdm-page/)：** 提供动作扩散建模的基础。MEO采用带动作上下文条件的补全网络，并将语言处理放在程序生成层；不能将其理解为只修改文本提示后重跑原MDM。[§3–4][paper]
- **[MoMask](https://ericguo5513.github.io/momask/)：** 支持掩码条件下的动作编辑。本文对照为它提供了MEO解析器确定的编辑时间，仍比较出不同的编辑保真与质量取舍，说明“找到掩码”只是完整编辑的一部分。[§5.3.1][paper]
- **[PoseFix](https://europe.naverlabs.com/research/publications/posefix-correcting-3d-human-poses-with-natural-language/)：** 用语言纠正3D姿态，关注单姿态修改。MEO还需要在源序列中选时刻、保留上下文、生成进出关键姿态的运动并支持多轮修改。[§3][paper]
- **[ProgMoGen](https://arxiv.org/abs/2405.19283)：** 同样把语言要求交给程序执行，但它的重要中间对象是可计算的动作目标/误差，再优化生成过程；MEO则以已有动作和编辑操作为出发点，先产生关键姿态再补全。两类“程序化控制”不应混成同一种接口。
- **启发：** 构建交互式动作系统时，可以分别设计“用户想改什么”“选择哪个源片段”“如何形成运动约束”“如何补出动作”四个接口，再对最后的动作验证要求是否成立。MEO提供了这条链路的具体先例，也说明模块可解释并不自动带来全局约束满足。
