## 一句话总结

MG-MotionLLM把整段动作的语义摘要、每半秒左右的身体部位描述和离散动作码放进同一个T5任务框架，先用**28种粗细粒度任务互相建立对应关系**，再针对具体任务微调；其中通用预训练模型可以完成“生成动作→解释为脚本→用户修改脚本→重新生成”的编辑循环。[§3–4；补充材料B、F、G][paper]

关键贡献是跨粒度训练与可读编辑接口。脚本中的时间和身体描述是模型条件，最终连续动作由VQ-VAE解码得到；论文没有把它实现为逐关节约束求解器，也没有证明未编辑区域逐帧不变。

## 研究背景与动机

**领域现状：** 文本动作模型既能从“一人向前走”生成动作，也能给动作写摘要；MotionGPT一类方法进一步把这两种方向放在同一语言模型里。

**现有痛点：** 整句摘要遗漏身体部位、动作方向与发生时间。用户想把“1.0–1.5秒的左前臂再抬高一点”，仅改整段caption很难精确表达；已有统一模型也主要学习全局摘要与动作的对应。

**核心矛盾：** 细节越充分，文本越长：全文脚本可能超过1,000个文本token，动作却只有不超过约50个离散token。直接把详细描述加进条件，模型未必知道哪些词对应哪个局部动作，甚至会损害语义匹配。

**本文目标：** 让同一个框架既理解整体动作，又描述、定位和生成局部身体运动，并把这种双向能力用于空间、时间及两者结合的编辑。

**切入角度：** 利用FineMotion已有的时间分段身体描述，构造从整段到片段、从描述到时间、从动作到脚本等辅助任务，先学较容易的局部对应，再把它们与全局语义连接起来。

**核心 idea：** 粗粒度任务提供“在做什么”，细粒度任务提供“何时、哪个部位、怎样运动”。通过粒度协同预训练共享表示，让两类监督互相帮助，而不是指望单次长提示自动获得局部理解。

## 方法详解

### 整体框架

模型由**冻结后的动作VQ-VAE**和**扩充词表的T5编码器—解码器**组成。输入可以混合自然语言、动作码、时间和脚本；输出按任务选择文本、时间或动作码。训练先准备动作量化器，再做28任务预训练，最后分支到任务微调。编辑演示使用通用预训练模型，并非必须串联四个不同模型。[图2、§3；补充材料F][paper]

图中两种“离散表示”不能混为一谈：motion script是可读的自然语言描述，动作token是学习得到的码本索引。前者经T5影响后者，再由连续解码器产生关节运动；不存在把一句“抬手”直接编译成确定关节角的规则表。

### 关键设计

1. **先把动作变成语言模型能够处理的有限词表。**

   模型采用T2M-GPT的VQ-VAE。对动作序列M，编码器产生降采样后的连续特征，再做最近邻量化：

   <div class="equation">Z = E(M)；cᵢ = argminₖ ‖zᵢ − bₖ‖₂；重建动作 M̂ = D([b꜀₁, …, b꜀ₙ])。</div>

   量化器用重建、embedding与commitment损失训练，随后冻结。本文实验采用HumanML3D的263维运动表示。因此T5预测的是码本编号，输出仍需经过查表和动作解码器；这些编号没有人工指定的关节或语义标签。[式1–2、§3.1、§4.1][paper]

2. **用特殊符号保留动作段与脚本的组织结构。**

   扩充词表包含原有文本词、动作码与特殊标记。`<Motion Tokens>`和`</Motion Tokens>`界定动作码段；`<SEP>`分开相邻时间片的详细描述；无显著身体部位运动的片段用`<Motionless>`表示。这里的“无显著运动”是标注状态，不等于所有关节严格静止。[§3.2][paper]

   FineMotion在HumanML3D动作上增加420,968个固定时间片的描述；补充材料示例以0.5秒间隔排列。21,346个片段有人工标注，约占5%；人工版本优先，其余使用自动描述。它不是全部重新人工采集的动作数据，也不是完全无标注学习。[补充材料B、图5][supp]

3. **28种任务分摊“长脚本对短动作码”的学习难度。**

   预训练包括12种经典粗粒度任务与16种细粒度任务，涉及文本、时间、动作三类信息。除了常规双向翻译，还要求模型根据局部描述找时间、根据时间找片段、结合摘要与脚本生成动作，或在给定头部、尾部及零散动作码时补全。[§3.3、表1；补充材料表8–10][paper]

   | 任务输入 | 模型输出 | 训练的对应关系 |
   | --- | --- | --- |
   | 整段动作 | 摘要、完整脚本或两者 | 运动到不同语言粒度 |
   | 整段动作 + 一段脚本 | 起止时间 | 局部身体描述在动作中的定位 |
   | 整段动作 + 时间区间 | 该区间的脚本或动作片段 | 时间与局部内容对应 |
   | 摘要 + 完整脚本 | 动作码 | 全局语义和局部细节共同生成 |
   | 摘要 + 脚本 + 头/尾/零散动作码，可带时间 | 动作码 | 多条件运动生成与补全 |

   这张表是28项任务的归纳，不是新增任务。作者刻意**排除仅靠详细脚本生成动作**的训练任务：走路和跑步都可能被描述成“双腿交替向前后移动”，需要粗摘要消除语义歧义。因此不能省略摘要后仍假定有同等支持。

4. **共享预训练模型负责多任务，任务专用微调追求单项性能。**

   T5按输入指令自回归预测输出token，以交叉熵训练。粒度协同阶段混合28项任务；由于每项只占总样本的一小部分，之后分别用目标任务数据继续微调。主结果中的任务最优模型与“一个预训练模型能完成整个编辑循环”是两种评估设置。[式3、§3.3–4.3][paper]

   官方仓库也分别发布`GSPretrained-*`和`t2m / m2t / tdt2m / m2dt`微调模型。不能把这些任务分支的最佳数字描述为一个固定检查点同时达到的成绩。[官方模型列表][code]

5. **编辑发生在可读脚本层，运动仍通过条件生成重新产生。**

   用户先获得初始动作及其脚本，然后修改某个时段的描述、插入静止片段、增加动作次数或删除尾部片段，再把原摘要与新脚本送回同一个通用模型。空间编辑改局部身体描述；时间编辑改脚本片段的数量与顺序。[§4.2、图3；补充材料F、图8][paper]

   论文当前流程需要用户手工改脚本。把简短编辑命令自动转成脚本修改是作者提出的后续方向，不能写成已经实现的第二个LLM规划器。生成过程中也没有公开描述的IK投影、接触约束或未编辑帧硬拷贝步骤。

### 一个完整例子：把看手表时的左前臂抬得更高

下面沿用论文图3的编辑类型，中文脚本为教学转述，不是本次运行输出。

1. 给通用预训练模型输入摘要：“一个人把左手腕抬到面前，好像在看手表。”模型输出动作码，经VQ-VAE解码得到初始动作。
2. 把该动作码送入动作理解任务，模型写出按时间片排列的脚本；例如1.0–1.5秒为“抬起左前臂到面部附近”。脚本是模型预测，因此可能漏掉或误写真实运动。
3. 用户将该片段改成“进一步抬高左前臂，达到头部高度”，保留其余脚本和粗摘要。这里编辑的是语言条件，不是直接修改关节坐标。
4. 使用“摘要+详细脚本→动作”任务重新生成token，再解码为完整连续动作。结果应通过关节轨迹和原动作对比检查左臂高度、发生时段及其他部位变化。
5. 若要求手必须到达某个精确三维点，或者右臂逐帧完全保留，论文的文本脚本与质量指标尚不能给出这样的保证；需要额外约束执行和实测。

### 训练与推理流程

**训练：** 用动作数据训练VQ-VAE并冻结 → 为HumanML3D准备动作码与FineMotion脚本 → 用扩充词表的T5混合预训练28任务 → 根据目标任务微调。不是用外部大模型在推理时临时解释每帧动作。

**推理：** 指令决定任务和输出类型；动作输入先量化，文字输入按扩展词表编码；T5逐token生成直到终止符或长度上限。动作码输出查码本并连续解码，文字/时间输出则直接返回给用户或下一个任务。[§3.1–3.3][paper]

## 实验关键数据

### 评估设置与指标

HumanML3D包含14,616条动作、44,970条序列级文字；FineMotion补充这些动作的分段描述。动作生成使用FID、R-Precision、MM-Dist、Diversity与Multimodality；文字任务使用BLEU、ROUGE、BERTScore及文本动作检索指标。粗粒度检索评估器来自已有训练好的配对模型，不能直接衡量某个关节在指定时刻是否满足命令。[§4.1][paper]

### 消融一：究竟是多粒度预训练还是单任务微调起作用

| --- | --- | --- | --- | --- | --- |
| 无 | 是 | .773 / .485 | .750 / **.148** | 2.969 / .516 | 62.34 / 50.5 |
| 仅粗粒度 | 否 | .725 / .862 | — | 3.433 / .431 | — |
| 仅细粒度 | 否 | — | .718 / .328 | — | 55.32 / 43.1 |
| 粗+细 | 否 | .767 / .540 | .771 / .313 | 2.942 / .514 | 62.87 / 47.7 |
| 粗+细 | 是 | **.802 / .303** | **.779** / .195 | **2.581 / .592** | **66.44 / 52.3** |

做了什么：改变预训练任务粒度，并比较是否接着进行任务微调。结果：粗细联合比只训练一种粒度更全面；后续微调明显改善目标任务。但**并非每项数值都单调改善**：无预训练时细粒度生成的FID .148优于最终.195；联合预训练但不微调的粗生成Top-3 .767也略低于直接微调.773。更好的语义匹配与更低分布距离不能混为一谈。

| Large，770M | .782 / .401 | .763 / .281 | .573 / **37.9** | 66.29 / **52.4** |

做了什么：比较三个T5规格。结果：Base在生成与检索上通常更好，Large在部分语言质量指标上更高；增大参数不保证提升。作者将其与HumanML3D规模有限联系起来，这是一种解释，论文没有单独证明数据规模是唯一原因。

补充材料D、图6另训练28个模型，每次从预训练任务中删除一项，以三项代表任务的平均Top-1检索率比较；作者报告所有删除设置均低于完整28任务设置。影响最大的三项依次为文本生成动作、动作同时生成摘要与脚本、结合摘要/脚本/时间/零散动作的生成。原图未列逐点精确数字，因此这里不从折线图虚构小数表；若被删除的任务恰好是评估任务，则只平均另外两项，比较口径也有所变化。

### 编辑证据覆盖到哪里

图3、补充图8展示了抬高左前臂、延长站立、额外跳跃、删掉动作尾段等案例；这些是定性编辑证据。论文没有提供系统性的局部关节误差、未编辑区域保持率、接触成功率或逐条命令满足率。因此“有时间片的可读控制”与“精确执行每个时间约束”应分开评估。

## 亮点与洞察

- **可读中间表示来自双向任务。** 同一个模型既写脚本又消费脚本，用户可以查看和修订模型对动作的解释；相比只提供潜变量滑杆，这个接口更贴近动作编辑意图。
- **时间定位任务补上了仅靠生成难学的对应关系。** 模型不仅回答“生成什么”，还学习“这段描述发生在哪里”。这种训练设计比单纯延长prompt更接近局部控制所需的监督。
- **保留全局摘要是有理由的。** 局部身体运动可跨动作语义共享，细描述不一定包含走路与跑步的判别信息；粗细条件互补并非只是把更多文字拼在一起。
- **统一能力与最佳任务表现被分阶段组织。** 一个共享预训练模型提供多功能接口，各任务微调追求专项性能。对系统设计而言，可根据需要选择单检查点便利性或专用模型效果，代价与收益应分别衡量。

<span id="reading-6" class="reading-anchor"></span>
## 局限与展望

- **脚本不是硬约束程序。** 没有明确的关节目标求解和轨迹投影；语义检索与文字相似度无法证明控制命令被逐帧执行。源动作编辑后是否完整保留未修改区域，也需要额外验证。
- **编辑依赖人工改写。** 当前用户需要修改详细脚本，平均7.1秒动作约有14个时间片。用外部LLM把自然语言编辑命令转换为脚本，是补充材料提出的未来工作。
- **标注误差会传播。** FineMotion大部分描述自动产生，动作到脚本的预测也可能出错。若把错误脚本当作准确运动说明再编辑，会积累偏差。
- **动作范围有限。** 补充材料明确未覆盖精细面部表情和手指手势，多人、动物及人—物交互也是扩展方向；“手臂抬起”不能等同于生成完整手部指形。
- **离散量化与规模限制仍在。** 细节经过动作压缩，T5放大没有一致收益；也未验证分钟级连续交互、实时首帧延迟或语音/音乐与文本同时控制。
- **指标与使用目标有距离。** 原有评估器偏向粗语义；最终需要时间边界、身体部位误差、未编辑区域保持和用户可用性测试，才能判断该接口能否成为可靠的动作编辑器。

<span id="reading-7" class="reading-anchor"></span>
## 相关工作与启发

- **MotionGPT、TM2T：** 前提是动作码与语言可以双向翻译；MG-MotionLLM继承这种接口并增加细脚本、时间定位及28任务协同。表3摘要基线数字来自既有论文，属于报告值比较。
- **T2M-GPT、MoMask：** 它们说明离散动作建模可以获得很好的生成质量；本文直接借用前者的量化器路线，但重点转向多任务可读控制。表2中的MoMask仍有更好的FID，不能以统一能力替代质量比较。
- **FineMoGen、FineMotion：** 细粒度监督需要带时间与身体部位的信息；本文用FineMotion重标注HumanML3D，而非自行发现完全无监督的动作语义。数据层的对齐与模型执行保证是不同问题。
- **CoMo及语言编辑方法：** 可读描述为用户提供修改入口；本文通过通用模型生成完整动作，而不是把脚本改动直接等同于几何局部替换。若用于交互角色，建议另加坐标空间约束与输出验证，此为本文解读提出的工程启发。
- **对动作规划系统的启发：** 可以把“全局摘要+分段身体脚本”作为可检查的中间条件，同时独立维护精确的时间、接触或目标约束。论文验证了前一层的可用性，后一层需要额外求解机制和实测，不能由可读token自动获得。
